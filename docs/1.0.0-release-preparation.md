# PopRaKo Server 1.0.0 发版准备

以 [仓库就绪审查](1.0.0-repository-readiness-audit.md) 为输入，按发布门槛、测试、
升级支持、文档清理、行为风险和最终切换六个方向验收。当前处于准备阶段，不能据此打 tag。

## 单 commit 发布约束

1.0.0 将清空旧提交历史，只保留包含最终仓库快照的一个根 commit。
旧提交 SHA、旧分支和旧 CI 记录只表示历史背景，不能充当新根 commit 的发布证据。
不得先部署旧 SHA，再重建历史并将新 SHA 标记为已部署。

顺序固定为：完成快照清理与版本更新 → 创建唯一根 commit → 更新 `main` →
对新 SHA 完成 CI、独立审批与生产部署 → 创建 annotated `v1.0.0` tag →
由 Release workflow 验证并发布。历史重写和远端更新是正式切换操作，准备工作不执行它们。

清空 Git 历史不清空数据库。已应用迁移的真实回滚来源、受支持升级工具、当前规范及
必须留存的运维记录都要在最终快照或受控运维档案中独立保存；不能再写“必要时从 Git 找回”。
旧 tag、旧分支及其他引用是否保留也必须在切换时处理，只替换 `main` 不等于移除所有旧引用。

发布证据只接受首次 attempt 即完整成功的 `main push` CI。GitHub 审批历史不带 attempt
身份，重跑记录无法证明审批属于哪次部署，因此不能用它补齐发布证据。重跑仍可用于排查；
正式验收需形成新的受审快照 SHA 并重新推送 `main`。1.0.0 重新生成唯一根快照，仍保持一个 commit。

## GitHub 外部设置

2026-10-25 只读核验结果：

- `main` 为默认分支，`Protect main` ruleset 已启用，禁止删除和非 fast-forward 更新。
  正式历史替换必须安排受控切换并恢复规则；本轮不修改 ruleset。
- ruleset 当前要求 Rust、TypeScript、Diesel migrations 和 Dependency security 四项检查，
  PR required approval 数为 0。发布前需确认维护者期望的 PR 审核策略。
- `production` environment 当前只有分支策略，没有 required reviewers。
  必须配置独立审批人和 prevent self-review，才符合 [Release Policy](../RELEASE.md)。
- `integration` environment 已存在但没有 protection rules。需限制可部署分支，并确认
  `INTEGRATION_R2_ACCOUNT_ID`、`INTEGRATION_R2_ACCESS_KEY_ID`、
  `INTEGRATION_R2_SECRET_ACCESS_KEY`、`INTEGRATION_R2_BUCKET_NAME` 和
  `INTEGRATION_R2_CUSTOM_DOMAIN` 指向独立测试资源。当前 token 对列出环境 secrets 返回 403，
  其存在性尚未核验；不读取或记录任何 secret 值。
- 环境列表没有 `release` 或 `staging`。正式发布前配置 release 环境策略，并在受保护的
  staging 完成部署与回滚演练。不要将 production 回滚当作演练入口。

HTTP job 不向 PR 提供 R2 凭据。`main` push 必须完成 HTTP suite 才能发布生产镜像；
缺少测试凭据会明确失败，不能按跳过处理。测试上传会写入实际 R2 测试桶，不能使用生产桶。
