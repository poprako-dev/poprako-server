## 1. 正式发布前应处理的维护机制

### 1.3 Release 流程仍有未完成的衔接

对照 [RELEASE.md](../RELEASE.md)、[release.yml](../.github/workflows/release.yml)
和 [ci-release.sh](../scripts/ci-release.sh)，存在以下差距：

- Release job 调用 pnpm 检查，却没有普通 CI 中的 `setup-js.sh`，没有保证约定的 Node/pnpm 环境。
- 仓库内没有校验 tag 对应已成功部署的 `main` 提交，也没有校验 tag 版本与 Cargo 版本一致。
- 政策要求的镜像身份、审批人和部署结果没有进入发布产物；所谓 SBOM 当前实际输出的是 `cargo metadata`。
- [Cargo.toml](../Cargo.toml) 和生成的 [OpenAPI](swagger.json) 仍是 `0.1.0`。
- [CHANGELOG.md](../CHANGELOG.md) 只有组织迁移基础设施的一条 Unreleased 记录。

版本号与变更日志可以在正式发布提交中完成；其余流程衔接应先补齐。
GitHub 外部保护规则和审批配置未在本次审查中核验。

## 5. 测试应保留，但 CI 执行范围需要补齐

[ci-test.sh](../scripts/ci-test.sh) 只运行默认 feature 的 workspace tests，
而不少数据库回归受 `rdb + repo_impl/prom_impl` 控制。
[ci-typecheck.sh](../scripts/ci-typecheck.sh) 只安装依赖并进行静态检查，不运行 HTTP 集成测试。

因此，all-features 编译通过不能代表这些回归已经执行。
正式维护应让关键数据库和 HTTP 回归进入明确的验证流程，
避免留下“测试文件存在，但发布前不执行”的状态。

这不是删除测试的理由，也不表示所有数据库测试都没有被执行；
需要按照各测试模块实际的 feature gate 和 CI 调用逐项确认覆盖范围。
