# 通用 Prom 的 use case 调用与重试约束

本文件记录 Lubover 明确要求的设计边界。后续修改、审查和解释通用 Prom 时必须遵守，不能用队列框架的默认假设覆盖这些约束。

## 不得假定 use case 幂等

- **use case 默认不是幂等的，禁止以其幂等作为 Prom 设计或正确性证明的前提。**
- 事务由 use case 内部开启。actor 在外面开启事务，不代表 use case 的数据库操作加入了该事务，也不代表 actor 能回滚已经提交的业务修改。
- 不得把“至少一次投递，所以 use case 必须幂等”当作解决方案。必须先证明具体 use case 可以被重复调用，才允许接入可能重复执行的消费路径。
- 不能因为 use case 名字包含 `try`、某个操作使用条件 UPDATE、当前示例恰好重复执行无害，就推导整个 use case 可以安全重试。必须覆盖全部数据库修改、事务提交和副作用。

## 哪些 use case 可以由 Prom actor 调用

调用准入必须检查完整执行契约：

1. use case 开启哪些事务，何时提交，是否存在多个独立事务或事务外写入。
2. 成功返回前后是否发送 effect、请求对象存储、调用外部服务或产生其他不能随数据库事务回滚的副作用。
3. 返回错误是否能证明业务没有提交、没有留下副作用；是否可能已经提交部分或全部结果后才报错。
4. 成功后、任务确认前进程崩溃，再执行同一任务会产生什么结果。

只有调用契约与 actor 的执行、恢复策略相容，才能接入。具体分类：

| use case 类型 | 准入与重试要求 |
| --- | --- |
| 真正没有写入和副作用的查询 | 通常可以重复执行；仍需考虑读取结果变化对后续处理的影响 |
| 有明确、经过验证的重复调用安全契约 | 仅在该契约覆盖的输入、失败和崩溃场景内允许重复执行 |
| 非幂等，失败时能证明完整回滚且没有其他副作用 | 该次已确认回滚的失败可以重试；这不意味着成功后的确认失败、超时或崩溃也可以重试 |
| 非幂等，内部自行提交事务 | 默认不能接入会在确认失败或超时后自动重放的消费路径；需要先改变调用契约或恢复机制 |
| 部分提交、提交结果未知或副作用结果未知 | 禁止盲目自动重试；必须先查明结果，或进入明确的待核查处理流程 |

“可以调用一次”与“可以交给具有自动恢复能力的队列长期运行”是不同的准入条件。不能只验证正常成功路径。

## 哪些失败可以安全重试

- 执行前即失败，并且可以证明没有业务修改或副作用：可以按既定策略重试。
- use case 明确报告整个执行已回滚，且没有事务外副作用：可以重试这次失败。
- 单凭 `Err`、错误名称为 Retryable、网络断开、超时、panic 或 actor 取消，不能证明内部事务已回滚。
- 提交返回错误可能存在结果不确定性；不能一概当作“提交没有发生”。
- use case 已成功，但任务删除或确认失败：**不能据此再次执行非幂等 use case。**
- processing 超时只说明 actor 没有及时确认任务，不能证明业务没有提交；不能仅凭时间自动重放非幂等业务。
- 限制重试次数、增加重试间隔，只限制损害次数，不提供重复执行安全性。

## UUID token 的保障范围

claim token 只隔离队列记录的回写：旧执行不能用旧 token 删除、重试或终结新领取的任务。

它不阻止旧执行已经进入 use case，不回滚 use case 内部事务，不保证业务只提交一次，也不使非幂等 use case 自动变得可重试。

任务行锁、actor 外层事务和成功即删除，也不能单独弥补独立业务事务与任务确认之间的提交窗口。
