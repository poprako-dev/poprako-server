# Release Policy

`main` is the production branch. Every merge to `main` runs required CI and,
after production-environment approval, deploys an immutable container tagged
`poprako-server-prod:sha-<full-commit>`. That full commit and Docker image ID
are the deployment identity and rollback key.

Cargo packages share one semantic version. Annotated `vMAJOR.MINOR.PATCH` tags
and GitHub Releases are created only from a successfully deployed `main`
commit. Patch releases contain compatible fixes, minor releases add compatible
behavior, and major releases may change public API contracts. The container SHA
tag remains authoritative even when a semantic tag exists.

Release notes are maintained in `docs/releases/MAJOR.MINOR.PATCH.md` and summarized
in a matching versioned section of `CHANGELOG.md`. They describe shipped behavior,
compatibility, upgrade requirements, and known limitations independently of Git
history. An application maintainer prepares a release; a production
environment reviewer approves deployment. The person who prepared a release
must not be its sole production approver.

Release artifacts must be built by GitHub Actions after required CI succeeds,
never on a maintainer machine. Each GitHub Release retains the source archive,
binary checksum, SBOM, provenance generated by the workflow, source commit,
image identity, approver, and deployment result. Exercise deployment and
rollback in the protected staging environment before the first
organization-owned release.

## First stable release

Version 1.0.0 starts a new Git history with exactly one root commit containing
the reviewed repository snapshot. Complete the cleanup and version updates
before creating that commit. History replacement and its remote update are
separate release operations; ordinary preparation does not execute them.

Validate, build, approve, and deploy the new root commit on `main` before
creating its annotated `v1.0.0` tag. CI or deployment evidence for a commit from
the previous history cannot qualify the new SHA. Retain required operational
records and genuine applied migration sources in the snapshot; Git history
replacement does not reset database migration history or authorize data loss.

## Automated release gates

`sh scripts/ci-release-check.sh --tag vMAJOR.MINOR.PATCH` checks Cargo workspace
and lockfile versions, generated OpenAPI, CHANGELOG, and versioned notes without
building artifacts. The workflow adds `--deployed --output FILE` to require:

- An annotated tag matching the checkout and a commit reachable from `main`.
- Exactly one root commit across all fetched branches and tags for `v1.0.0`.
- A successful `main` push CI run at that exact SHA, including database-backed
  Rust tests, migrations, security, image build, and deployment.
- The CI run must succeed on its first attempt. GitHub's approval-history API
  does not identify attempts, so reruns cannot establish which deployment was
  approved. Reruns remain useful for diagnosis; release qualification requires
  a new reviewed snapshot and `main` push. For 1.0.0, recreate the single root
  snapshot rather than adding another commit.
- A production approval independent of the CI initiator, rerun initiator, and
  release initiator, plus retained deployment evidence from that workflow attempt.
- The immutable GHCR digest, local image tag, Docker image ID, and successful
  deployment result reported by the remote deployment script.

Configure production required reviewers and prevent self-review in GitHub before
releasing. HTTP integration is not executed by GitHub Actions and no
object-storage credentials are stored there. Run `sh scripts/ci-http.sh` locally
against a disposable database and a dedicated non-production R2 test bucket
before requesting release approval; CI and pull requests only type-check the
integration test sources.

The release workflow provisions the same independent Node.js/pnpm toolchain as
CI. It publishes a tracked-source archive including checked-out submodules,
Linux binary archive, binary and artifact checksums, a CycloneDX 1.5 SBOM produced
by pinned cargo-cyclonedx 0.5.9, and workflow provenance with deployment and
approval evidence. The provenance JSON is a workflow record, not a signed
attestation. Deployment evidence is retained in Actions for 90 days and copied
into the GitHub Release; publish within that retention window. Expired evidence
requires a new reviewed snapshot with fresh CI, approval, and deployment.
